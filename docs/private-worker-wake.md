# Private worker wake, opt-in draft

This code is OFF by default. Nothing in this PR provisions an identity, applies SQL, changes Supabase settings, changes a credential, deploys, merges, or restarts a worker. The proposed SQL is deliberately outside `supabase/migrations`; the ordinary migration runner cannot activate it. The old polling mode remains unchanged until an approved rollout enables the replacement on the Mac.

## Behavior

Set `CONDUIT_WAKE_ENABLED=true` on both approved API and worker deployments only after completing the gates below. The worker also requires `CONDUIT_WAKE_CONFIG_FILE`, a local file with `url` (the exact HTTPS Supabase project origin), `publishableKey` (an `sb_publishable_` public key), `topic` (`conduit:pool:shared`), and `sessionFile` (absolute path to a private 0600 dedicated machine Auth session). Session fields are `access_token`, `refresh_token`, and `expires_at` in Unix seconds. Never use an owner session or service-role/signing/DB credential. Do not put these files in Git, logs, job text, or chat.

One outbound private Broadcast socket per worker process joins a fixed shared-dispatch topic. It accepts only `work_available` with `{v:1}` with only optional UUID `id` metadata added by Supabase; hints never supply tasks or commands. The socket is not an inbound listener and cannot wake a sleeping Mac. The existing authenticated queue remains authoritative. Startup, successful subscription/reconnect, explicit hints, job completion, and a six-hour fallback scan reconcile PRs and fill up to four execution slots. New hints can fill vacant slots while other jobs run. Signals during a scan remain pending. Scans are spaced at least five seconds under storms. Idle operation makes no periodic HTTP heartbeat, empty-claim, or 30-second PR reconciliation loop. Existing active execution renewals, heartbeat calls, lease durations, fences, and quarantine/paused-work rules are unchanged.

All existing journals are validated before the transport starts. A recovery barrier settles pre-existing journals before fresh claims. Any failed cycle/reconciliation stops new work and preserves recovery state instead of polling or discarding it. The normal worker lock/origin binding remains in force. A socket authorization rejection stops the process; transient connection errors back off up to five minutes. A hosted `MissingPartition: ` join error uses that bounded reconnect path; authorization, invalid-token and unknown join errors remain fatal. A cold service may create vendor-managed message partitions only after an initial connection. Do not edit vendor partitions to clear this error. Session tokens are cached; 25-second socket keepalives do not call Conduit. Near-expiry refresh goes directly to Supabase and rotated refresh material is atomically saved privately before use.

### Honest observation status

`GET /api/workers` adds `observation_status` (`recent` or `unknown`), `observation_as_of` (the actual last API observation), and `wake_subscription_status: "unobserved"`. No claim is made that a socket is currently connected, a machine is awake, or a slot is free. The existing `available` field and its 15-second freshness window remain for compatibility. The legacy GUI's stale/offline text is a stale API observation, not proof of disconnection in wake mode. Use the additive fields for monitoring; don't extend leases or turn a stale worker green. Future dedicated idle-presence UI can consume these fields without heartbeat traffic.

## Durable signaling and limits

Review-only SQL installs a fixed-pool generation/outbox row with `enabled=false`. Queue INSERT / transition to queued covers simple jobs, roots, revisions and explicit retry; initiative transition to active covers initial activation and resume of already-queued work; verified PR false-to-true merge observation signals before claim-time dependency promotion; project re-enable records a hint. All record in the original transaction, so rollback emits nothing. Hints never bypass any eligibility check. Completion locally refills slots without new server state.

After a successful API operation that can produce wake state, the API calls one narrowly granted outbox helper. It locks/coalesces generations, uses fixed `realtime.send` with a constant tiny private payload, and records delivery only after confirming the private Broadcast row was inserted (the hosted helper can swallow send errors as warnings). Failure retains pending generation with a five-minute retry delay. Publication is at least once, not exactly once or client-acknowledged delivery. Database send success does not prove socket receipt. A concurrent producer cannot lose its generation behind a successful drain. There is no added hosted sweeper, cron, or periodic flush request. Pending delivery is retried on a later successful wake-producing API operation. A failed publish may therefore wait until a later eligible API operation or fallback. Startup/reconnect/six-hour scans cover lost hints.

External GitHub merges have no webhook here. They and abandoned expired-job recovery can wait up to the six-hour fallback or an explicit wake. An offline/asleep Mac catches up only after it runs again. Six hours is an idle queue fallback, not zero network: Supabase socket keepalives, auth refresh, reconnects and active jobs still use network. Quotas and token expiry must be checked before activation.

## Explicit wake route

`POST /api/worker-wake`, JSON `{}`, UUID `Idempotency-Key`, requires `jobs:wake`, a submitter identity and an administrator-reviewed `wake_callers` grant. Existing keys and console sessions do NOT gain this scope automatically. No URL, pool, topic, job, command, retry or resume parameter is accepted. The helper resolves the existing shared pool; per-caller serialization limits new accepted IDs to one per minute. An identical previously accepted UUID is accepted without another signal. 202 means the hint was accepted, never execution or delivery; response explicitly says `delivered:false`. 429 uses `Retry-After: 60`. Disabled API returns 404. The request-id ledger currently retains IDs; review storage retention before long-lived production use. No new scope is provisioned by this change.

## Required rollout approvals, in order

1. Review the exact PR head, tests, current PostgreSQL role/default grants and the proposed SQL. Prove that no pre-existing permissive Realtime policy widens the intended receiver policy. Test against a disposable real Supabase project/channel first. Local PostgreSQL stubs are not a Realtime service test.
2. Approve production schema/policy changes separately. The SQL has a fixed search path, PUBLIC revocation, receive-only exact subject/topic policy, and no authenticated table access. It necessarily grants schema USAGE so the policy helper can be called; this must not expose tables, other helpers, Storage, console authority, or Data API schemas. Audit all existing function EXECUTE grants as well as table grants before approval. No broad service credential belongs on the Mac.
3. Approve a dedicated machine Supabase Auth identity and private session, not mapped in `orchestrator.auth_users`. Provision a public publishable key and short-lived scoped authenticated session. Verify denial for wrong subject/topic, anon/public joins, Broadcast INSERT and Presence; verify no queue/key/auth mapping/storage/Data API read or owner-console action. Verify refresh rotation, expiry, revocation latency and interruption recovery with the real service. Audit whether Auth signup/profile defaults add unrelated privileges. Policy revocation is cached until token refresh/expiry; disabling a mapping alone is not instant disconnection.
4. Approve private-only Realtime setting and fixed shared-pool subscriber mapping. Existing dispatch is shared across owners, not per-owner routing. Review recipients for that pool. Approve narrow caller grant/scope only if an operator needs the hosted wake route. No implicit key upgrade. Review ledger retention.
5. Approve merge/auto-deployment, then explicit configuration and DB enablement. Verify the publisher in isolation while no real work runs. Enable the outbox only after receiver/auth checks. Existing rejected Claude diagnostic/quarantine work remains untouched.
6. Approve the Mac configuration and restart. Verify the exclusive lock, clean journals, cached token refresh, subscription, four-slot claim/refill, reconnection, six-hour fallback, active renewal/fencing and rollback on the exact deployed build. Measure Vercel request counts before claiming savings. Do not test with new paid jobs, credentials or settings without approval.

Rollback: disable worker wake mode and restart only with approval to restore original polling. Disable API flag and DB control; retain journals, pending generations and request ledger for investigation. Do not drop state, remove locks, rotate credentials, or resume paused/quarantined jobs as part of rollback. Reverting the code alone does not revoke already-issued machine sessions; revocation is a separate approved account operation.

## Request budget

Legacy idle worker: four loops each heartbeat+claim every two seconds, up to 4 HTTP requests/second before latency (86,400 per six hours), plus idle PR reconciliation around 30 seconds. Enabled steady idle: one fallback sweep per six hours, one pending/reconciliation scan plus up to four empty claims. Reconciliation may add one call per pending PR, and a hint/connection completion can cause bounded additional sweeps. Active jobs keep all original renewal traffic. Supabase keepalives occur separately and are not Conduit/Vercel requests. This is a design budget, not measured production savings. PM twice-daily checks are separate.
